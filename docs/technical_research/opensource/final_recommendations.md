# 最终建议（final_recommendations.md）

## 六个问题的直接回答

**1. 是否存在明显的重复造轮子？**
不存在。协议解析（HLS/FLV 交给 hls.js/mpegts.js）、数据库（sqlx）、播放（成熟库）均未手写；平台适配层的自主实现是领域必需（无官方 API）。唯一「重复」是 5 个适配器间 150-200 行请求样板（P2 抽 helper）与 **sea-orm 死依赖**（引入了但从未用）。

**2. 哪些已有代码值得保留？**
database/（sqlx 仓储）、adapter.rs trait 设计、auth.rs、播放链路、updater、飘屏、webctx 页面环境架构——占代码量大头，质量良好。

**3. 哪些模块值得局部优化？**
弹幕重连（OPP-1，P1 核心）、UTF-8 panic（OPP-2）、斗鱼签名竞态（OPP-3）、前端 unlisten 泄漏（OPP-5）、searchScope 重搜 bug（OPP-6）、hls 网络恢复（OPP-9）。

**4. 哪些模块有必要替换？**
无。最接近替换门槛的是播放器内核（libmpv），但飘屏 DOM 架构 + 无性能证据使其停留在 P2 观察。

**5. 哪些第三方依赖值得引入？**
运行时依赖：**零新增**（全部问题用现有栈局部优化解决）。工具链：cargo-deny 进 CI（P2）。

**6. 哪些开源项目仅适合架构参考？**
streamlink（插件制）、OpenPlayer（双窗口分层，mpv 路线启用时照此）、blivedm_rs（弹幕健壮性细节）、bilibili-API-collect（协议文档）。

**7. 优先处理什么？**
OPP-1 弹幕重连 → OPP-2/3 panic 与竞态 → OPP-4 死依赖清理（三个 P1 一次清完约半天）。

**8. 整体架构是否适合继续发展？**
适合。平台适配器 trait 使新增平台成本低；webctx 页面环境架构已把最高风险的逆向签名问题收敛为「页面内 fetch」；前后端规模（9k/3.6k 行）仍在直觉可维护范围。

**9. 下一步最值得投入？**
OPP-1~4 的 P1 批次（稳定性+清理，半天量级）→ 然后**新功能开发优先于架构工程**（产品面仍是最有价值投入方向：多窗口观看、开播提醒深化等）。
